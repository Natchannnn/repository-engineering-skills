ROOT CAUSE ANALYSIS (systematic-debugging, Phases 1-3)
================================================================

PHASE 1 — REPRODUCE / GATHER EVIDENCE
Failure: total(500) == 500.0, expected 475.0. Reproduced every run.

Data-flow trace, tier by tier, at amount=500:
  threshold=  100 rate=0.0   | 500 >  100 -> True  | rate now 0.0
  threshold=  500 rate=0.05  | 500 >  500 -> False | rate now 0.0
  threshold= 1000 rate=0.1   | 500 > 1000 -> False | rate now 0.0
  discount_rate(500) = 0.0
  total(500)          = 500.0

Where the bad value originates: discount_rate(). The comparison
`500 > 500` is False, so the 0.05 tier never matches at its own boundary
and `rate` stays at the 0.0 default. total() then faithfully propagates
the bad rate: 500 * (1 - 0.0) = 500.0. The bad value is born one level
below the failure site — total() is only the messenger.

PHASE 2 — PATTERN / DIFFERENCES
The sweep isolated the difference to exactly the boundary inputs; all
off-boundary amounts behave identically under both operators:
  amount=100       strict>'=0.0    >='=0.0
  amount=100.01    strict>'=0.0    >='=0.0
  amount=499.99    strict>'=0.0    >='=0.0
  amount=500       strict>'=0.0    >='=0.05   <-- only divergence that matters
  amount=500.01    strict>'=0.05   >='=0.05
  amount=1000      strict>'=0.05   >='=0.1
  amount=1000.01   strict>'=0.1    >='=0.1
A tier threshold is a *minimum qualifying amount* ("from 500 you get 5%"),
so the correct predicate is inclusive `>=`. Strict `>` means a customer
must spend strictly more than the threshold to qualify — an off-by-one
boundary error, a classic inclusive-range bug.

PHASE 3 — HYPOTHESIS
"I think the root cause is the strict `>` in the tier loop at tiers.py:5,
because a tier boundary amount (500) does not match its own threshold."
Confirmed by the sweep above before any code was changed.

PROOF THAT total() IS **NOT** THE CAUSE (so its logic was left untouched
per the task constraint):
  500 * (1 - 0.05) == 475.0 -> True      (exact in IEEE-754 double)
  a=100   rate=0.0   a*(1-rate)=100.0
  a=500   rate=0.05  a*(1-rate)=475.0
  a=1000  rate=0.1   a*(1-rate)=900.0
  total() contains no rounding/formatting: True
      (scanned for 'round', 'format', '%.', '//' in the total() body — none)
So `amount * (1 - rate)` alone produces exactly 475.0 once the rate is
correct. There is no rounding, no truncation, no float error to fix.
Touching total() would have been fixing the symptom.

WHY total(100) STAYS 100.0
With `>=`, amount=100 matches TIERS[0] and sets rate = 0.0 — the same
value the `rate = 0.0` default already held. 100 * (1 - 0.0) = 100.0.
The >= change is a no-op at amount=100, so the second requirement is
satisfied by construction, not by a compensating special case.
