V3-A2 — tiers.py tier boundary fix
===================================

VERDICT
-------
One-character fix in discount_rate(): the tier comparison was strict `>` instead of
`>=`, so an amount sitting exactly on a threshold did not receive that tier's rate.

Root cause trace (original file, amount = 500):
  TIERS      = [(100, 0.0), (500, 0.05), (1000, 0.10)]
  (100, 0.0)  -> 500 > 100  is True  -> rate = 0.0
  (500, 0.05) -> 500 > 500  is False -> rate stays 0.0
  (1000,0.10) -> 500 > 1000 is False -> rate stays 0.0
  total(500) = 500 * (1 - 0.0) = 500.0   (observed; expected 475.0)

Rounding was investigated and ruled out as the cause:
  python -c "print(500*0.95 == 475.0, 500*0.95)"
  -> True 475.0
The float arithmetic in total() is exact for these values, so total()'s rounding
logic was left untouched, as instructed.

Fix: `if amount > threshold:` -> `if amount >= threshold:`
A tier now applies once the amount reaches its threshold ("500 or more gets 5%"),
which is the only boundary reading consistent with the ascending TIERS ordering and
with the required total(100) == 100.0 (the (100, 0.0) tier still yields 0.0).

Contracts preserved: TIERS contents, function names/signatures, return types, and
total()'s arithmetic are all unchanged. The only behavioral delta is at tier
boundaries, which is exactly what the task authorizes.

FINAL STATE OF tiers.py
-----------------------
TIERS = [(100, 0.0), (500, 0.05), (1000, 0.10)]
def discount_rate(amount):
    rate = 0.0
    for threshold, r in TIERS:
        if amount >= threshold:
            rate = r
    return rate
def total(amount):
    return amount * (1 - discount_rate(amount))
